## Что проверяется по всем 104 городам

Команда `python -m app.place_freshness --format json --check` выполняет инвентаризацию **каждого текущего места**: название, уникальный slug, город, категорию, персональную ссылку на источник, дату документации, возраст источника, тип происхождения (OSM, Wikidata, редакционные/институциональные ресурсы), необходимость и приоритет ручной проверки. Для каждого города считает объекты и высокий приоритет. Отдельно хранит подтверждённые архивные объекты и проверяет, что ни один такой slug снова не появился в `CityCatalog` или готовых маршрутах.

Результат размещается в GitHub Actions: шаг **Full catalog freshness inventory and retired-place guard**, артефакт **place-freshness-inventory** и таблица по всем городам в `GITHUB_STEP_SUMMARY`.

**Важно:** наличие страницы (даже с HTTP 200), OSM/Wikidata-записи, координат или недавней даты `PlaceSource.checked_at` **не доказывает существование, открытость, доступность входа и пригодность пешеходного перехода**. Дата `checked_at` означает дату документирования сведений, а не независимый осмотр места. Инвентаризация покрывает все карточки, но не даёт права говорить, что все карточки независимо подтверждены на сегодняшний день.

## Полный редакционный аудит по шагам

1. Для каждого объекта проверить существование: официальный первичный источник, сообщение о закрытии/демонтаже, официальный городской реестр. В случае противоречия проверить публикации двух независимых организаций и дату сообщения.
2. Для действующих объектов подтвердить адрес и фактическую точку входа, категорию и ограничения доступа. Для платных и закрытых помещений — часы, покупку билетов, перенос экспозиций и временные перерывы. Для парков — стройки и доступность дорожек.
3. Изменения вести в отдельном реестре с `city_slug`, `place_slug`, типом события, датой и ≥1 конкретной ссылкой. При подтверждённом демонтаже исключить из живого каталога, генераторов маршрутов и готовых экскурсий без очистки сохранённых записей пользователей; старый идентификатор оставить в `RETIRED`.
4. Перепроверить ссылки и фактические переходы готовых маршрутов. Геодезическая близость не гарантирует доступный пешеходный маршрут.
5. Не подменять недоказанные факты `active` или `verified`. Для непроверенных карточек фиксировать **needs_independent_current_verification**; предоставлять прозрачное предупреждение пользователю.

В 59 новых городских каталогах картографические данные по-прежнему имеют статус `map_seed`, не статус редакционно проверенного гида. Проверка полного количества карточек и источников — это **техническая инвентаризация**, а не 100%-ная полевая и актуальная проверка. Полная независимая проверка каждой точки остаётся открытой редакционной задачей.

### Массовый контроль всех 104 городов

`python -m app.place_source_probe` по умолчанию создаёт строго **офлайн** реестр 2 142 карточек и 104 городов. С `--live --output place-source-scan.json` инструмент сверяет исходные URL с публичными HTTP-страницами, данные OSM — с текущими элементами OSM API, Wikidata — с текущими записями API. Каждая карточка остаётся в результате и содержит сигнал изменений.

Запланированный `Place Source Watch` запускается по понедельникам в 05:17 UTC, при изменениях связанных исходных файлов в `main` и вручную. Артефакт `place-source-scan` содержит результаты **для каждой карточки каждого города**. Ошибки HTTP 403/429, сетевые сбои или отсутствие OSM-записи — сигнал для перепроверки, **не основание автоматически снимать объект с публикации**. Аналогично успешный HTTP 200 — это только доступность ссылки, а не подтверждение открытости.

`app.place_evidence` и API Mini App предоставляют текущий статус и первичный URL отдельно от `PlaceSource.checked_at`. Не выдавайте URL-проверку и картографическую метку за независимую проверку доступа, точного входа, часов или состояния пешеходного маршрута. Без ручного подтверждения остается задача проверить объекты во всех городах, несмотря на полный машинный охват источников.

## MVP-131 — приоритизированная очередь из массовой проверки

После каждого сетевого запуска `Place Source Watch` создаёт **второй артефакт** — `place-review-queue` с JSON и Markdown. Он покрывает все 104 города, включает 2141 активную карточку и один временно исключённый объект Нальчика (цифры за 11.10.2026). Для рискованных точек привязаны **конкретный город, slug, исходный URL, последнее изменение источника и все готовые маршруты с этой остановкой**. Таким образом редактор видит, что именно исправлять.

Порядок обработки:
1. `P0_documentary_investigation`: OSM lifecycle (стройка, снос, заброшенность, запрет доступа) или завершение работы по Wikidata. **Это ещё не доказательство сноса или закрытия**. Проверить официальный операторский источник, решение муниципалитета и фотографии/публикации, затем принять решение об исключении или предупреждении.
2. `P1_source_identity_review`: исчезнувшая страница, запись OSM или Wikidata. Возможно, объект переименован или заменён другим идентификатором; **не удалять без независимых доказательств**.
3. `P2_retry_or_manual_source`: HTTP 403/429 и сетевые/серверные ошибки; перепроверить URL вручную либо у второго независимого источника.
4. `P0_withheld_until_operator_opening`: точки, снятые с публикации из-за отсутствия доказанного открытия (например, Нальчик). Сохраняются в отдельном списке до проверяемого уведомления оператора; одних изменений OSM недостаточно.

CLI для анализа ранее скачанных результатов:
```bash
python -m app.place_review_queue --scan place-source-scan.json --output place-review-queue.json --markdown place-review-queue.md
```
Для сравнения с предыдущим запуском поддерживается `--previous previous-place-source-scan.json`, чтобы выделить изменившиеся сигналы. При пропущенных карточках/провисших ссылках/неизвестных типах сигналов очередь **завершает работу ошибкой**, а не умалчивает неполноту. GitHub Actions показывает первые 30 рисков и сводку по 104 городам, а полный JSON содержит все случаи и затронутые маршруты.

**Блокер полной верификации:** официальный перечень работающих объектов, подтверждённые адреса входов, часы и право прохода отсутствуют в API OSM/Wikidata и простых HTTP-ответах. Это требует редакционного расследования и, для некоторых объектов, подтверждения на месте; тестами нельзя достоверно заменить независимую проверку 2127 пока неподтверждённых мест.

## MVP-133 — корректная проверка русскоязычных URL

В очереди MVP-131 **12 карточек Дербента** имели `UnicodeEncodeError` при попытке проверить общий официальный URL `https://derbenttourism.ru/достопримечательности/`. Это **ошибка клиента при передаче пути**, а не свидетельство закрытия сайта или объектов.

Сетевой клиент теперь преобразует международные IRI в корректный percent-encoded HTTPS URL **перед запросом** (`/достопримечательности/` → `/%D0.../`). Оригинальная адресная ссылка и идентификатор POI сохраняются неизменными; существующие `%XX` не кодируются повторно. Заголовки, статус и временные перенаправления по-прежнему не используются для объявления достопримечательности существующей. Схемы кроме HTTPS и ссылки со встроенными учётными данными отклоняются. При повторном запуске мониторинга 12 записей должны перейти из ошибочного `UnicodeEncodeError` в корректный результат HTTP либо независимую сетевую ошибку, если сам сервер недоступен.


## MVP-134 — изменения относительно предыдущей еженедельной проверки

Для нового `Place Source Watch` GitHub Actions читает самый свежий **успешный** предыдущий запуск одноимённого workflow через GitHub API и загружает его `place-source-scan` в рабочий каталог CI. Текущий скан остаётся полным для 104 городов. `place_review_queue` сравнивает предыдущие и текущие сигналы **по паре city_slug/place_slug**, отмечает `new_or_changed`, подсчитывает изменения и в каждой категории риска поднимает их в начало очереди. Результат отражается в JSON-артефакте и GitHub Actions Summary.

Если предыдущего запуска нет или артефакт недоступен, текущая проверка всё равно создаёт полную очередь, но честно сообщает `previous_scan_available=false`. Изменения HTTP/OSM/Wikidata — сигналы расследования, а не доказательство фактического закрытия/открытия. Права workflow ограничены `contents: read` и `actions: read`; он ничего не публикует автоматически и не редактирует пользовательскую базу.


## MVP-135 — исправление ложных сетевых тревог и контроль смещений картографических точек

Реальный запуск мониторинга 11 октября 2026 года (GitHub Actions `38126459864`) показал **204 технические ошибки проверки ссылок**, сосредоточенные примерно в **42 доменах**: недоступность одного сайта, например `culture.ru` или `gotoomsk.ru`, вызывает много предупреждений о разных достопримечательностях. При этом `gotoomsk.ru` доступен через независимый поисковый интерфейс и показывает календарь октября 2026 года. Поэтому HTTP-сбои не означают ни закрытия сайта для всех пользователей, ни исчезновения объекта.

После этой доработки:

- Для HTTP `HEAD` со статусом 403, 405 или 501 разрешена **одна** повторная попытка `GET`. Для 429 (rate limit) повторов нет. Успешный GET доказывает только доступность URL, а не функционирование туристической точки.
- Очередь группирует технические сигналы **по домену**: сколько отдельных карточек и городов за ним стоит, сколько готовых маршрутов затронуто, какие ошибки DNS/HTTP встречаются. Это помогает исправить один общий источник вместо ошибочного объявления многих объектов неактуальными.
- Для OSM **node** сравниваются сохранённые координаты с координатами текущего элемента. Смещение на **500 метров или больше** даёт `mapped_coordinates_changed_review_required` и приоритет `P1_location_review`, чтобы редактор проверил адрес и маршруты; это **не автоматическое обновление координат** и не доказательство переезда или закрытия. Для OSM `way` и `relation` без текущего центроида сравнение не проводится, отсутствие координат не считается перемещением.
- Некорректная широта или долгота в результате OSM помечается как отдельный повод для расследования. Уже обнаруженные теги строительства или сноса сохраняют приоритет и не маскируются координатной проверкой.

Отчёты `Place Source Watch` и артефакты `place-review-queue` содержат таблицу крупнейших проблемных доменов, индивидуальные координатные смещения и затронутые `route_slugs` в JSON. Никаких автоматических удалений или подтверждений существования не производится. Для реальной актуализации неизбежно требуется независимое подтверждение музейного режима, состояния парков и достоверных входов/маршрутов.
